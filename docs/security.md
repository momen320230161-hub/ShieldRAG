# Security architecture

The [Task 06.1 security review](security-quality.md) documents current model selection, bounded exact excerpts, security controls and remaining semantic-grounding limits.

Requests cross three boundaries: HTTP bearer authentication, trusted profile RBAC, and Supabase RLS. None of the read routes uses a secret or service-role key. A role is refreshed from trusted `profiles` data on each request, avoiding authorization based on stale JWT metadata. User-editable metadata, HTTP headers such as `X-Role`, and query parameters cannot promote an account. Task 03 adds a separate trusted server-write adapter for private Storage and tightly scoped registration/review RPCs after these authentication and permission checks.

`require_admin` protects approval/rejection and indexing routes and remains reusable for future evaluation operations. The document list returns approved metadata; detail metadata follows uploader/Admin/approved-public RLS. RAG calls the user-scoped search RPC, requires approved and verified fully indexed sources, and rechecks current roles and sources before returning generated answers. `can_retrieve_document` remains a defense-in-depth metadata guard.

Security event reads follow existing RLS: Students see only their own events, Admins see all, and rows without a user are Admin-only. Both query and response filtering enforce this boundary. Upload and successful review RPCs create events atomically with metadata/state updates. Integrity denials now persist `document_integrity_failure / deny` independently before Python returns 409. The reviewer/document IDs come from verified identity and trusted document metadata; SHA-256 mismatch uses the fixed reason `SHA-256 mismatch detected`. No file bytes, tokens, credentials, raw request fields, or observed hash are stored in the event. No arbitrary event-writing endpoint exists.

Invalid tokens return 401, permission failures and absent/unrecognized profiles return 403, and upstream service failures return sanitized 503 responses. Recognized Supabase Auth error codes handle invalid JWTs reported upstream as 403. Keys and bearer tokens are omitted from response models and principal representations. No authentication bypass or development token feature exists. Supabase validates the JWT remotely; unit tests mock that verifier's results rather than pretending to prove cryptography. Live tests exercise password sign-in, genuine signed access tokens, and invalid/tampered tokens.

RLS tests in `backend/tests/rls_rollback.sql` create synthetic fixtures inside a rolled-back transaction. They test effective authenticated roles, forged metadata, role/update denial, security event ownership, approved-only chunks and the RPC. This SQL must run through an authorized operator connection. It does not test stolen-session revocation or external network controls. Access tokens remain valid according to Supabase session and expiration behavior; instant revocation on every endpoint is not promised.

Task 03 privileged writes use `SUPABASE_SECRET_KEY` only after validating the user's identity and trusted role. Upload allows Students/Admins; review requires Admin in both Python and the database. The two write RPCs use SECURITY INVOKER with a fixed empty search path and execute grants only to service_role. Existing RLS and retrieval policies are unchanged. SHA-256 is rechecked before approval, and row locking serializes competing review transitions with their audit writes. See [ingestion security and compensation limits](document-ingestion.md); Storage and PostgreSQL are not a distributed transaction.

Task 03.1 adds only `shield_record_integrity_failure` through forward migration `20261115130214_shieldrag_integrity_failure_audit`. It is also fixed-search-path SECURITY INVOKER, executable only by service_role. It independently checks the trusted Admin profile, document existence, and the expected hash/path association. Failure kinds and reasons are fixed in SQL. Existing table RLS and grants are unchanged; even an Admin JWT cannot directly invoke this server RPC or insert/update events through PostgREST.

Each review attempt generates a server-only UUID. Audit insertion uses the existing `security_events.id` primary key to deduplicate an internal retry, verifies that an existing ID belongs to the same actor/document/failure, and returns an explicit UUID acknowledgement. One uncertain acknowledgement can be retried with that same UUID. The audit transaction commits separately from the rejected approval, and never changes document status. A pending document stays pending; the audit operation does not undo another legitimate concurrent review.

An unconfirmed audit write fails closed with HTTP 503 and a UUID-only operational log; approval never proceeds. Revoked Admin rights or a disappeared document still produce 403/404. If a commit succeeds but both acknowledgements are lost, an event may already exist even though the API returns 503. Independent HTTP review requests intentionally create independent events; retry deduplication is not a client idempotency protocol. No durable audit retry queue or unrelated recovery worker was added.

Task 04 independently revalidates original SHA-256 immediately before extraction and again before atomic index publication. Approval remains an earlier integrity observation. [Baseline RAG](rag.md) documents service-only write leases, stronger indexed/hash/consent RLS, caller-token retrieval, current-role rechecks, citation validation, external processing authorization and remaining prompt-injection risks.

Task 04.1 makes completed-index verification read-only. A cache hit creates no lease and invokes no generic job cleanup; transient infrastructure failure, timeout, cancellation or an unavailable Gemini service cannot delete or mark that completed revision failed. Generic failure transitions require `index_status=processing` and the exact job UUID, and retain all existing chunk rows. Confirmed integrity failures use the new service-only `shield_invalidate_index`: the existing fixed-reason/idempotent audit and revision-scoped retrieval revocation commit together. Chunks are retained for investigation but hidden from both roles by existing RLS. Stale observations and audit replays cannot change a newer completed revision. Missing-object classification still requires a recognized Storage response, not a timeout or 5xx. Database unavailability can prevent durable audit/revocation; the request remains denied, emits a UUID-only reconciliation log and never falls back to deleting completed data.

The final Task 04.1 Security Advisor reports the existing **Leaked Password Protection Disabled** Auth warning, with no database/RLS finding. An earlier check in the same task returned no findings; the final result is reported here. This task did not change Auth settings. Operators should [enable leaked-password protection](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). See the current [verification report](verification.md). Advisors do not replace direct permission tests, ongoing dependency updates, deployment hardening, or future pipeline security evaluation.

The full live suite uses a separate operator-only SQL fixture adapter. It temporarily commits uniquely marked Auth accounts and synthetic documents/chunks, then removes them with guarded cleanup. It never adds privileged operations to the web application. Secrets stay in ignored local files, JWTs stay in test-process memory, and synthetic sessions are logged out. Auth audit records may remain according to platform retention; they are not deleted. Cleanup removes fixture users/profiles/documents/chunks and relies on Auth-owned cascades for sessions/identities. SQL fixture provisioning is tied to the inspected managed Auth schema and must be reviewed after platform changes. Crashed runs require manual guarded cleanup, and access-token revocation semantics remain those of Supabase.

## Task 05 Security Agent

The secure endpoint adds input/context/output rule and classifier checks while retaining the same authoritative Auth/RBAC/RLS and original index integrity conditions. The agent is never an authorization authority. Review decisions are non-allow; unsafe context blocks the whole request; output failures withhold all raw output and citations. Existing baseline safeguards are preserved. [Security Agent documentation](security-agent.md) records the threat model, synthetic dataset, measured false positives/misses, artifact trust boundary and paired comparisons.

`shield_record_security_decision` is service-only SECURITY INVOKER with fixed empty search_path, fixed reason/version fields, trusted actor/document association and UUID replay checks. It adds no direct user write permissions or RLS changes. Both allowed and denied secure responses require audit acknowledgement. Audit failure returns a safe structured 503; it does not release a successful answer. No raw prompts, source content, responses, credentials or classifier feature values are stored in events. No durable audit queue is introduced.

The JSON numerical model bundle is repository-trusted, digest-checked and bounded. The loader accepts the bundled numerical model and manifest, with no pickle or joblib deserialization. An attacker controlling application code and the release manifest is outside this integrity boundary. Task 05.1 calibrates non-allow thresholds using validation data and requires each supported secure answer to be one exact span of a validated citation quote. The previously observed mock contamination is withheld. Benign refusals and the risk of misleading or missed malicious content already present in authorized excerpts remain. See [measured results and limits](security-agent.md).
